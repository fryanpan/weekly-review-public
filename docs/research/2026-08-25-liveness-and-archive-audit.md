# Liveness signals and archive integrity — measurement record (2026-08-25)

Full provenance for the peer review of the claude-workspaces wake protocol and
the archive audits it turned up. **This file is deliberately NOT loaded into
every session** — `docs/process/learnings.md` carries the transferable rules and
points here for the numbers. Grep this when you need to re-derive one.

Outcome: the review killed the 20-minute watchdog. Transcript-growth liveness —
the replacement I proposed — was pulled from the build too, on the grounds that
it was equally unmeasured. Scope that shipped is the dependency gate only.

Peer review of the claude-workspaces wake protocol, whose watchdog would call an in-progress task dead after 20 minutes with no task activity (comment, transition, body edit, linked PR). The question routed to me was whether that signal is derivable and sufficient.

- **`stat` succeeds where `open` fails, so a freshness probe can pass on a volume it cannot read.** Team Lead measured this under launchd on 2026-08-25: `/bin/bash`, `/bin/ls`, `/usr/bin/head` and `/usr/bin/rsync` are all denied on `/Volumes/Data`, while `~/.bun/bin/bun` — which lives on that same denied volume — reads a 162MB transcript fine. **The gate is per-binary, not per-path:** Apple *platform* binaries inherit launchd's empty TCC identity (corroborated here from `codesign` — `/bin/bash` has no Developer ID authority; `bun` is Developer-ID signed with hardened runtime and gets its own identity). Two consequences: **relocating the script off the volume is not the fix** (a relocated bash script dies on its first `cp`), and any scheduled check must *read a byte*, never trust `stat`. B11 opens a file for exactly this reason — don't "optimise" it back to a stat.
- **B11: unarchived backlog, the check B10 cannot be.** B10 asks "is the archive fresh" from inside the run that just refreshed it. B11 asks how many live-store files have **never** been copied and how old the oldest is — independent of the refresh, and alarming at 21 days against an observed ~16-week live-store rotation. First run: 77 unarchived, oldest 1d (healthy — today's sessions). Note B10 passed the same run at **20.5h lag against a 24h threshold**, i.e. it was hours from firing anyway.
- **"Archived" by name is not "archived" — and the gap is worst exactly when it matters.** Transcripts are append-only, so an active session keeps growing after its first copy lands, and both B11 and Team Lead's independent implementation count it as archived forever after. During an outage the long-running sessions are simultaneously the ones that grow and the ones that already have a name in the mirror, so the backlog count understates the loss. B11b asserts the sound half: a transcript that **settled before the archiver last ran** must not be short in the mirror. Files still newer than the last pass are lag, not loss. Currently 0 short, 55MB in flight.
- **Two independent implementations agreeing is weaker evidence than it feels.** Mine and Team Lead's returned identical numbers (77 unarchived, oldest 0.7d) in different languages — which rules out a coding bug in either, and rules out nothing about a shared assumption, because we both keyed on the session id. Same shape as the agreement-laundering entry above.
- **A name→path dict silently picks a loser when the name is not unique.** 256 session ids appear under more than one project dir in `mac_mini/` (576 across the whole archive root — scope the count, the two numbers are both right). `{f.name: f}` let a **15KB** copy shadow the same session's fully-archived **130MB** copy under a different project, and I was one message from reporting a fabricated 136MB permanent data gap. Key by **max size per name**, and treat any id→path map over this corpus as many-to-one until proven otherwise.
- **I described that shadow as a "0-byte stub" and it is 15,459 bytes** — a `:.1f` print in MB rendered it `0.0`. A peer took the description literally, searched their tree for zero-byte copies, correctly found **none** (there are zero in the entire archive), and reported a non-reproduction. The mechanism was real and my size class was not, so the search predicate I handed them could not have matched. **When warning a peer about a defect, give them the query, not your rendering of the output** — a rounded number becomes a false claim the moment someone tests it.
- **Derivable, yes — 824 of 905 activity events on the LF board are agent-emitted.** "A working agent emits these for free" is true. That is not where the design fails.
- **Sufficient, no: the median gap between consecutive activity events is 16.7 min** (p75 51, p90 227, p95 758). Any threshold near 20 minutes sits at the median of *healthy* cadence, so 72% of intervals that ended in `done`/`review`/`blocked` contained one.
- **The gap histogram alone proves nothing** — a silence may be overnight or a legitimate human-gated hold. The measurement that indicts a liveness proxy is silence *while the subject is provably active*, which needs an independent witness. Transcripts are that witness: cut them into runs with no internal gap longer than the window (so real idleness is excluded by construction), then measure board silence inside each run. **71% of provably-active runs, and 40% of provably-active minutes, would have read as dead.**
- **Density is the whole story: 93,160 transcript events vs 1,279 board events over the same 8 days, 73×.** A 587-min run emitting 102 board events still went 98 min silent. Activity events cluster at milestone boundaries — a burst when something lands, then nothing through the next build/read/debug loop — so chattiness doesn't rescue the proxy. **Any liveness check must run on a signal denser than the thing it is trying to detect.**
- **Generalize before publishing a number: this was one board, the fleet's fastest.** A peer with a single-operator board and multi-day human-approval holds would have every hold read as a stall. The reframe that survives both corners is dependency state, not elapsed time — the right variable, not a better constant.
- **The published caveat was whole-board silence vs whole-project transcript activity.** Per-task silence is strictly longer (so the number understates), but concurrent worktrees mean the active session wasn't provably the one holding that task. Say that in the report rather than letting the cleaner-sounding number travel.
- **The append-only transcript is the cheap liveness primitive.** `stat` is O(1), costs no tokens, needs no agent cooperation, and can't be gamed by posting to satisfy a timer. Same necessary-condition logic as `archive_window_coverage()`. Resolve it by session id, never by cwd — see [[session identity]] above; a cwd-derived path lands on an empty worktree dir 12 times in 14 and reads as permanent death.
- **Three outcomes, not two — and I got this wrong first.** I flagged the worktree/cwd trap and then prescribed cwd resolution in the same breath; a peer checked it against real directories and found 12 of 14 empty, which looked like the mechanism failing rather than my rule failing. Corrected: `file missing` means **the watcher is blind**, not that the subject is dead, and those need different alerts. `file exists` is not alive either — one transcript last written four weeks ago satisfies an existence check forever. Only **grew since the last observation** means alive, and the first observation can only set a baseline.
- **Both of us shipped a confident wrong answer from a working tool.** Their `find` choked on the leading `-` in the directory names, with stderr suppressed, and returned a clean `0 transcripts` for a directory holding a live 127MB file. Exit code zero, tidy output, false. "I looked and saw nothing" and "I could not look" are the same string at the surface — which is the same lesson as the archive gate, arriving from the opposite direction.

- **Replicated on a second board, and the one I picked first couldn't answer.** `crm-tool` has 7 tasks and **zero completed in-progress intervals** — nothing ever transitioned through in-progress, so the measurement has no denominator there. Report that, don't silently substitute a board that works. `ca-4128-build tool` (63 tasks, 24 completed intervals, 163 gaps) does answer, and agrees with `live-feedback` while running slightly worse: median gap between consecutive task-activity events **14.8 min** (LF: 16.7), p75 **92.9 min**, and **84% of intervals that ended in done/review/blocked contain a 20+ minute silence** (LF: 72%). At a 10-minute window it is **100%** on both. A watchdog threshold set just above the median inter-event gap will fire on most healthy work by construction.
- **The honest counter-argument, stated because the numbers invite it:** the longest silences here sit inside multi-day intervals (up to 4,711 min), which include overnight — a task left in-progress at 2am is not being falsely accused of anything. That is exactly why the indicting measurement is the transcript cross-check, not the gap histogram: it restricts to spans where the agent was provably typing throughout. The histogram sets the shape; only the cross-check makes it a false-positive claim.
