# Learnings

## Transcript ingestion

- **Worktree conventions are inconsistent.** The user's repos use both `--claude-worktrees-<name>` (sibling dir with dash-dash prefix) and `/.claude/worktrees/<name>` (nested inside the repo). `projects.yaml` patterns must cover both. Missing either one routes events to the wrong slug.
- **System-injected "user messages" are everywhere.** Beyond `<system-reminder>` and skill-injection banners, real transcripts contain channel messages (`<channel source="claude-hive" ...`), scheduled-loop triggers, task-runner notifications (`<task-notification>`), and tool-result echoes. Filter them aggressively — they wrecked the first dry run's numbers.
- **Mixed timezones in events.** Git log emits local-TZ ISO strings; Claude transcripts emit UTC-Z. String-sorting the merged stream silently breaks `cognitive_wall_clock_seconds` (we got negative wall-clock on the first try). Always sort by `datetime.fromisoformat`, not by raw string.

## Segmentation

- **Project-proximity fallback is sufficient for ≥95% coverage without any LLM.** On a 2-week window with ~20 registered projects, coverage hit 100% with only Layer 1 rules + 7-day same-project proximity. The Layer 2 LLM classifier is still not needed.
- **Automated workloads will dominate "active hours" unless excluded.** The rare-disease-benchmark harness produced 1442 sessions and 1000s of user messages. Added `exclude: true` flag to projects — one-line config entry per excluded worktree.

## Configuration

- **`fnmatch` patterns are evaluated in order; first match wins.** Put exclude-rules BEFORE the project they live inside of (e.g. `rare-disease-benchmark` ahead of `health-tool`), otherwise the general pattern catches first.
- **`~/.config/weekly-review/` is the right layer for per-user knobs.** Repo examples in `examples/` seed a new user in < 2 minutes.

## Data window provenance

- **Clean data starts mid-April 2026 (~Apr 13).** Through W14 (Apr 6-12) the user ran a Cloudflare-hosted product-engineer R2 agent team in parallel with Claude Code; R2 transcript traffic ended Apr 12 (W09-W14 had 9.5k/4.7k/1.4k/4.3k/9.4k/1.3k R2 events, zero after). Mixing the Cloudflare-era weeks with the all-Claude-Code era confounds the leverage/speedup numbers (the dispatch-heavy R2 weeks inflate pooled ratios). **For consistent analysis use mid-April → present only** — that gives ~two months of clean, single-harness data as of mid-June. The user's call, 2026-06-12: "let's only look at April to present." The enriched windows inside the clean range so far: Apr 27, May 11-25, Jun 1.

## Effort formula

- **22h active / 61h cognitive / 14d window.** First real run gave an active/cognitive ratio of 0.37 — i.e., the user is in-conversation 37% of his thinking hours. Lower than 1.0 is expected (planning, reading, verification happen off-transcript). If this ratio were near 1.0 or above it'd signal the formula is missing real effort; if near 0.1 it'd signal over-capping.
- **The 20-min-per-message cap matters.** Without it, agent messages with massive reading-word counts produced absurd per-turn active times.
- **Pure-dispatch weeks produce 100x+ leverage and that's a real signal, not a bug.** W11-W12 (Mar 8-22) showed leverage of 328x and 126x with user-active 0.73h/0.57h, vs W14-W17's 29-51x with 6.5-13.7h. The difference is real: in W11-W12 the user dispatched almost everything via Slack to product-engineer R2 agents, so his keyboard-typing time collapsed to single dispatch lines while agent output kept flowing. The headline metric should expose dispatch-mode weeks distinctly — a 300x leverage week is not a 30x week multiplied by 10, it's a different working mode.

## Process

- **Dry run early, fix patterns iteratively.** First `--no-enrich` pass over real transcripts exposed 4 bugs (tz sort, excluded projects, missing system-msg patterns, worktree patterns) in under 15 minutes. Shipping a coarse pipeline first and iterating on real data is much faster than perfecting synthetic fixtures.

## Review-override carry-forward

- **Stable task IDs are NOT stable across a re-segmentation that changes task boundaries.** A verdict recorded against a task carries forward by `task_id`. When orphan-adoption / atomic split re-cuts a big task, the id can survive on a small fragment — so an 80h "whole-week MVP" verdict (2101 events) got stamped onto a re-cut ~60-line remnant (100 events) whose own LLM rationale said ~1.5h. It became the single largest (spurious) task in the window and inflated the substantial-tier bar + pooled totals. The per-task **median** headline was immune (one task), which is exactly why we lead with medians.
- **Guard: compare event_count then-vs-now.** `carry_forward_ok(baseline_events, current_events)` in `calibration.py` skips the override when the count diverged >3× since review (fail-safe on unknown counts). `load_review_overrides_with_context()` reads the baseline count from the DB that recorded the winning verdict. Verified: only the one bad case tripped it (21× ratio); legit 1-event digest overrides are 1.0×.
- **Cheap internal-consistency detector for corrupted estimates:** scan for tasks where the stored `est_human_hours` disagrees with the number in the LLM's own `rationale` text by ≥3×. Across 564 tasks this surfaced exactly the one override-corrupted row and nothing else — a good sanity check to run before publishing any estimate-weighted number.
- **est concentration ≫ hands-on concentration.** Top-50-by-est tasks were ~48% of estimated output but only ~19% of hands-on time — the biggest-estimate tasks are the most agent-leveraged, so they barely touch the keyboard-time denominator. Reviewing "the big ones" validates output-weighted leverage, not hands-on-weighted.

## Verdict ingestion & merges

- **Never re-parse a pre-filled ✅ verdict line as a new correction.** The worksheet pre-fills already-reviewed tasks with their recorded verdict text (e.g. "✅ reviewed: high — the user agreed with LLM raw response of **80h**"). A naive re-parse reads that "80h" back out and re-records it with a *newer* timestamp, so latest-wins picks the stale value and clobbers a later correction (429aa5d582 flipped 6h → back to 80h this way). Skip lines containing "reviewed:" / the ✅ marker when harvesting fresh verdicts.
- **A manual merge can trip the carry-forward guard on the merge TARGET's own review.** `_apply_manual_merges` grows the target task's event_count (104ec71e6f went 22 → 136 after absorbing the icons-rework task). The override guard (`carry_forward_ok`, >3× event divergence) then reads that as "task changed since review" and skips the user's *own* 0.5h verdict on it, falling back to the LLM est (3h). Fix for now: re-record the verdict against the post-merge run so baseline_ec matches. A cleaner future fix: exempt manual-merge targets from the divergence guard, or recompute their baseline after merge.

## Rework metric

- **Rework should not count as output.** When something shipped broken and had to be redone, the est_human_hours of the rework loop is waste, not value. Surface it as a separate "rework cost" line in the leverage block AND as a "Rework clusters" section in the digest. See `src/weekly_review/rework.py` and the integration in `digest.py` / `cli.py`.
- **Detection signals (in order of strength):** revert commits/PRs (5 pts), user frustration markers in user messages (3 pts each — "still broken", "bug is still there", "doesn't work", "default to the old"), `fix/revert-*` branches (5 pts). Per-task threshold to flag = 3; per-cluster threshold to surface in digest = 5. One isolated frustration marker is noise; multiple markers across tasks OR a revert is signal.
- **Cluster by (project, ≤72h gap).** Rework loops live in one project and resolve within a few days — broader windows mix unrelated work.
- **Don't use est_human_hours to bucket rework cost.** Use user-active + agent-active hours instead — they're directly measured and don't propagate LLM-enrichment noise. (est_h IS used for the `leverage_user_excl_rework` line as the numerator, with rework hours subtracted from the *denominator* — that's the cleanest single-number signal.)
- **Things that LOOK like rework but aren't.** Migrations done mostly hands-off (e.g. a blog repo → writing-tool), refactors triggered by user simplification request ("this is confusing, collapse modes"), and discovery work in unfamiliar territory. The detection regex set is tuned for false-positive rate over recall — when in doubt, don't flag.
- **Why "still" alone isn't enough.** The user uses "still" in non-rework contexts ("still need to add docs"). Pattern requires `still + (broken|not working|happening|wrong|there|failing|crashing)` and similar concrete-verb pairings.

## Artifact credit (est double-count fix, 2026-07-28)

- **The dominant est inflation was never per-task optimism — it was the same artifact estimated in several tasks.** The 100-estimate review found weekly est totals 25-60% hot from four shapes of double-credit: pr_opened and pr_merged routed to different tasks (each with the full diffstat), ship-shard "merge it" tasks inheriting the whole build's diffstat, a repo registered under two project slugs double-ingesting its commits, and opened+merged both summed inside one task's ARTIFACT TOTALS. Singly-attributed tasks with real labor were estimated well.
- **Fix at the enrichment-input level, not post-hoc.** `artifact_credit.py` assigns each artifact identity (repo+PR number; commit sha) to the ONE task holding the work evidence (most non-artifact events); other placements render in the prompt as "CREDITED TO ANOTHER TASK — do not count." Post-hoc subtraction can't work because est_h is a holistic LLM output, not a sum of artifact parts.
- **Commit identity must be sha-only.** The git extractor stamps `metadata.repo` with the project SLUG, so the same repo under two slugs carries different repo strings for identical commits — keying on (repo, sha) would break exactly the cross-slug case the dedup exists for.
- **PR events dedupe cross-slug by construction, commits don't.** github_pr session_ids embed the real owner/repo string, so two-slug PR ingestion collapses in dedupe_by_event_id; git_log session_ids embed the slug, so commits duplicate. Any new artifact extractor should embed a repo-stable (not slug-stable) session_id.

## Task-id carry-forward (2026-07-28)

- **Match re-segmented tasks to prior ids by event-set overlap, newest run first.** Score = max(Jaccard, coverage-of-old if Jaccard ≥ 0.2), threshold 0.5 — recovers 82% of churned ids; the rest are genuine splits that should re-key. The coverage term handles absorb cases; the Jaccard gate stops a mega-task claiming every tiny id it grazed.
- **Never key a rewrite loop by task_id.** The id mutates mid-loop once matched; key by object identity (`id(task)`), or the second prior-DB pass KeyErrors.

## Ops

- **The hourly transcript-archive LaunchAgent dies with "Operation not permitted" and it is NOT a TCC grant.** First seen Jul 15 (exit 126, 319h stale, caught by the B10 archive-freshness audit), again Aug 17 — script untouched, `-rwxr-xr-x`, runs cleanly from a terminal every time. This file recorded the cause as "macOS revoked launchd's TCC grants, re-grant Full Disk Access" **twice, and both times that was wrong.** The real mechanism, read off `/tmp/weekly-review-archive.err.log` on 2026-08-25: Apple-signed `/bin/bash` under launchd is denied all access to a second volume, and the user's whole home resolves there. **It fails at `exec` of the script** — `bash: /Users/<you>/.local/bin/archive-transcripts.sh: Operation not permitted` — so the process never reaches `~/.claude/projects` and a Full Disk Access grant cannot fix it. The fix is to get the interpreter and script off the denied volume, or off launchd. (Thanks to the lead agent for the volume mechanism.)
- **The log had the answer in one line and nobody read it for 17 days.** 395 identical hourly lines, one distinct string, created Aug 8 21:36 and still firing. Two silent recurrences were diagnosed by reasoning from a directory listing instead. `StandardErrorPath` is set on the plist; **read it before theorising.**

## Subagent / fan-out ingestion

- **Every dispatched agent keeps its own transcript**, at `<session>/subagents/agent-<hash>.jsonl`. This covers all three spawn types — Agent-tool subagents, Workflow agents (which also nest `subagents/workflows/wf_*/journal.jsonl`), and agent-team teammates (they're `in-process`, so they do NOT become separate top-level sessions). Subagent files are ~77% of the whole corpus (8,358 of 10,900 archived).
- **Subagent records carry the PARENT's `sessionId` and `cwd`.** Good: they merge into the parent's stream and attach to the right task in the right project. Bad: `seq` restarts at 0 per file, so `event_id = source:session:seq` COLLIDED across the main loop and every subagent — and `dedupe_by_event_id` silently discarded them. One research session: 1,624 lanes → 1, 80% of events destroyed. Fixed by putting the lane in the id (main-lane ids unchanged, so nothing persisted shifts). **Any id built from `(session, seq)` on transcript data is wrong** unless it also carries the lane.
- **A subagent's `user`-role records are the parent's dispatch prompt, not the user typing.** The extractor emits them as `kind=subagent_input, actor=agent`. Without that, multi-thousand-word dispatch prompts get scored as hands-on typing time and inflate the denominator of every leverage metric.
- **Workflow `journal.jsonl` is `started`/`result` records only** — the extractor's `user`/`assistant` filter skips it, so it contributes 0 events rather than garbage. Don't "fix" this.
- **Agent hours ≠ agent labor.** Agent hours merges all lanes into one timeline (elapsed), so N concurrent agents read as one. That's a legitimate definition, but it makes fan-out invisible — hence `agent_labor_hours` (per-lane, summed). Neither belongs in a leverage denominator: fan-out already pays off in the est_h numerator, so crediting it twice double-counts.
- **A blocked orchestrator is not a worker.** The dispatching parent is itself a lane and sits idle while children run; billing it would report 16 agents as 17. Detect blocked time from real child-lane activity, not tool names — that way Task, Workflow and team dispatches all behave the same.

## Machine traffic in the human lane (2026-08-17)

- **Peer relay is the biggest single contaminant of hands-on time.** When one session's message is injected into another's conversation it lands as an ordinary `user` record — no marker, no distinguishing field. In the Aug 10-16 week that was **132k of 155k "typed" words**. It scales with fleet size, so it has been getting worse silently: the more peers coordinate, the more "hands-on" time the human appears to spend. Filter `^Another Claude session sent a message` (wraps `<teammate-message>`, `<agent-message>`, `<cross-session-message>`).
- **`promptSource` is the structural tell, and it beats text matching.** `system` = cron/scheduled injection, `typed`/`queued` = the human. Prefer it over matching a particular user's cron prompt wording — the text approach doesn't generalize past one user, which matters for a public repo. `isMeta` marks harness bookkeeping. Peer relay carries NO promptSource, though, so you need both signals.
- **Agents sign as their project, not as "Agent".** A live-feedback denylist on the literal name "Agent" let through `Client A board`, `Live Feedback`, `Notes Repo`, `Health Tool`, `ca-agent` — **53k of 61k comment words**. Author filters must be ALLOWLISTS (identify the data subject positively). Bonus: an allowlist also correctly excludes a third-party reviewer, whose comments are real review but are not *the subject's* hands-on time.
- **Sanity-check the ratio in BOTH directions.** active/cognitive of 0.37 was the documented healthy value — but it was computed while both leaks were live, so it was inflated. Post-fix it is ~0.12. A ratio that looks "normal" is not evidence of a clean numerator; check what the numerator is made of.
- **Every published hands-on/leverage number predating these fixes is hot.** Not by the est_h double-count mechanism — this is a separate, additive error in the denominator. Historical trend needs a re-run before it can be quoted.
- **`promptSource: sdk` names the client, not the writer (2026-09-28).** Headless `claude -p` runs (cron jobs, test rigs, probes) send `sdk` with `entrypoint: sdk-cli`, and the filter let them through: a 1,442-word triage prompt at 09:00 every day read as a block of his typing, and he spotted it on the week page. But the desktop app also sends `sdk` (`entrypoint: claude-desktop`) for prompts he types. A scan of every `sdk` prompt since Aug 15 showed only cron jobs; the full archive showed the desktop ones too. **Key machine input on the pair, and scan the whole archive before trusting a field's meaning from one recent window.** Effect on the published series: 5 of 23 weeks moved, all upward in multiplier (largest Jul 13, 10.9x -> 11.5x).
- **"Only this week is affected" was a guess about history I had not scanned.** I told him the Sep 14 week was the only one; the scan found four more. Say "pending the archive scan" until it finishes.

## Hands-on is presence, not keystrokes (2026-08-17)

- **The per-message model measured typing, then called it working time.** `active_hours_by_task` charges a modeled reading+typing window around each message and nothing in between, so watching a build, reading a diff, driving a device by hand and thinking all scored zero. It reported 10.4h for a week the user put near 20h. He rejected it on sight; he was right.
- **A rejected number is a calibration event, not a complaint.** The subject is the only instrument that can falsify a time model. Sweep the parameter and show the table rather than defending the value: 5min→9.9h, 10min→18.3h, 15min→25.3h, 30min→37.4h. The 30min column exceeding stated capacity is what rules out the loose end; his reaction rules out the tight end. **State plainly that the result is a modelling choice inside a range, not a measurement.**
- **Check whether the challenge is about data or model before investigating.** The first hypothesis offered (stale archive) was already ruled out — 78,962 events, every weekday populated. Proving the window was present in one per-day table took one query and redirected the whole investigation to the real cause.
- **Union the stitched runs with the modeled windows, don't replace them.** An isolated message stitches to a zero-length span; unioning keeps its typing estimate, which guarantees presence >= active for every task and makes the new metric a strict improvement rather than a different trade-off.
- **The shares were stable across every tolerance; only the total moved.** QB 60-63% at all settings vs 46% under the per-message model. When a metric is contested, lead with the ratio that survives the parameter sweep.
- **Presence is defined per task and was never designed to be summed — so bound the double-count instead of assuming it away (2026-08-28).** Sum-of-parts >= their union, and the week-wide stitched union is itself a lower bound on the true union, so `Σ per-task − week-wide union` is a rigorous CEILING on the cross-task overcount. Measured 0.84h (4%) and 0.47h (3%) on the two August weeks — small enough that a weekly total is defensible. Two minutes of arithmetic, no new model. Related: audit #4 (`wall-clock ≥ hands-on`) fires ~25x per week under the presence model *by construction* — the modeled reading window starts before a task's first event, so a task's presence can exceed its own first→last span. That is an invariant written for the per-message model, not a defect; check the summed effect before chasing the per-task violations.
- **Run-to-run variance is real: ~±2% on an identical command.** Task-id carry-forward reads every prior run, so task boundaries shift slightly each time and a per-task sum moves with them (21.4 / 21.4 / 21.7h on one window). Quote hands-on to 0.1h, never to two decimals, and re-run once before treating a small delta between two runs as a finding.

## Off-keyboard work (2026-08-17)

- **Calendar recovers what transcripts structurally cannot.** A transcript-only pass reported zero reachouts for the Aug 10-16 week; the calendar showed a Thursday lunch. Any goal that lives in email, meetings or conversation reads as zero forever without it. **Report "no trace", never "did not happen."**
- **The CRM records intent; the calendar records outcome.** Notion's `Last Contacted` had one contact reading three months stale the day after a lunch with them, and a prospective client a week stale. Any "overdue" count computed from CRM dates alone is inflated by exactly that lag. Join them by attendee email and let the calendar win on what happened.
- **"Count only accepted events" silently drops recurring invites the user never RSVPs to.** The user is `needsAction` on the weekly client demo every week and attends anyway — a standing hour missing from every capacity model.
- **A gap in the calendar does not say whose move it is.** A prospective client read as ten days of silence; the ball was actually in their court. Report the gap, never the blame.

## Publishing history (2026-08-17)

- **This repo has NO pre-push scrub gate, and neither do most.** No `.githooks/`, `core.hooksPath` unset. A peer asserted the gate "runs on the diff automatically" and would block a leak; it does not exist. A fleet scan the same evening found **2 of ~40 repos** actually have one. An assumed gate is worse than a known-absent one, because it stops you looking. **"Configured" is not "has a gate"** — several repos set `core.hooksPath` to the default empty `.git/hooks`, and one points at a `.githooks/` containing only `post-checkout`. Test for the executable file at the resolved path:
- **The gate needs TWO things, and testing for the hook alone gives a false positive.** The `pre-push` hook has **two silent `exit 0` paths**: it resolves `scripts/scrub-check.py` *inside the repo being pushed* and no-ops when that is absent (deliberate, so peer repos aren't blocked), and it no-ops if `git rev-parse --show-toplevel` fails. Either way the hook runs, succeeds, and inspects nothing. So pointing `core.hooksPath` at a shared `.githooks/` (the obvious one-line "fix") installs a gate that does nothing while looking installed to any hook-only check. Test both:
  ```bash
  hp=$(git config core.hooksPath); hp=${hp:-.git/hooks}
  [ -x "$hp/pre-push" ] && [ -f scripts/scrub-check.py ] \
    && echo "GATED" || echo "NOT GATED (hook and script are both required)"
  ```
  Audited across 39 fleet repos 2026-08-17: 6 gated, 33 not, and zero false positives *today* — but the false-positive state is exactly what the config-only fix would create, so any rollout has to copy the script too.
- **Scrub BEFORE the squash, and sensitive text never enters pushed history.** A squash preserves the net diff, not the intermediate states. So if the already-pushed base is clean and everything sensitive lives in the unpushed range, scrubbing the working tree first means the rewrite drops the old text entirely — no force-push, no history surgery. Check the base first (`git grep <term> origin/<branch>`); that one command decides whether this is a five-minute job or a rewrite.
- **`git grep` searches tracked files only, so a clean scan can be a false negative *about scope*.** A filesystem `grep -r` found the tailnet hostname in four more files under `docs/data/` — which turned out to be gitignored, i.e. genuinely safe. Run both: `git grep` tells you what ships, plain `grep` tells you what exists, and the difference is what your `.gitignore` is protecting. Here it protects ~1.5 MB of raw transcript excerpts and the subject's own messages.
- **Anonymize third parties, keep the lesson.** Real names of contacts and prospective clients in a flip-public repo are *their* data, not the subject's, and the learning reads identically as "a contact" / "a prospective client". Don't delete the example — a lesson without its concrete case stops being memorable, and `learnings.md` loads into every session.
- **Don't fix portability bugs during a push cleanup.** `cli.py` hardcodes a fallback home path; that's a real defect for a public tool, but changing runtime path defaults while restructuring 84 commits mixes an untested behaviour change into a mechanical one. Flag it, ship the cleanup, fix it separately.
- **Squashing invalidates every commit hash you have cited elsewhere.** Three SHAs quoted in a provenance table died in the rewrite — the same "proof-shaped and wrong" failure the table was written to fix, in the opposite direction. Grep the docs for short SHAs after any history rewrite.

## Auditing a scorer (2026-08-17)

- **An audit that reads a subset of the input paths commits the very error it is auditing for.** A peer reported "scored positive on no evidence," having dumped two of its pipeline's enrichment fields and found them empty — a third path had enriched the record correctly. It scored a conclusion on incomplete evidence while filing a bug about scoring on incomplete evidence. Before trusting a "no evidence" finding, enumerate every path that can populate the evidence, not the ones you remember.
- **Agreement laundering: a hand-check that agrees with the verdict makes a story feel confirmed rather than checked.** It happened twice in one evening — a lucky score that manual review endorsed, and a bad finding that manual review endorsed. When the check and the thing checked can share a blind spot, agreement is weak evidence.
- **The audit must be cheaper and dumber than the thing it audits**, or you end up auditing the auditor. B4 has survived unchanged because it is a regex plus a ratio — no model, no thresholds to tune. Prefer a phrase list and a comparison over anything that itself needs judgement.
- **Generalizing a ratio check to a categorical verdict:** the analogue of "3×" is *ordinal distance*, not sentiment. Map the rationale to an implied bucket, flag `|implied − emitted| ≥ 2`. The ≥2 gap is what makes it usable — adjacent-bucket disagreement is normal imprecision and must not fire, exactly as 2× does not fire here.
- **The strongest categorical signal is a stated disqualifier that was not applied.** A rationale naming a hard exclusion ("onsite only", "won't take fractional") while the verdict stays positive is a near-certain bug rather than a judgement call — and it is a different failure from missing evidence, so an input-side evidence gate will never catch it.
- **An itemised confidence section is not evidence of correctness — it is evidence you enumerated the errors you already knew about (2026-08-28).** I published two weekly hands-on figures under a careful "±10%, here is what that is made of" heading: a measured 4% ceiling on double-counting, 2% run-to-run variance, 0.9% unattached events. Every one of those was right. Meanwhile **`--until` is INCLUSIVE, so both windows were 8 days long**, the two weeks overlapped on the boundary day, and the figures were hot by ~23% and ~9% — an error an order of magnitude larger than everything I had itemised, in a dimension I never thought to check. **The itemising made the number feel audited and made me stop looking.** Before publishing, check the shape of the window itself (how many days did I actually measure?), not only the noise inside it.
- **All 24 internal audits passed on an 8-day week; a peer's disagreement caught it.** Nothing in the pipeline knew how long the window was supposed to be, so no check could fire — the run printed coverage, hands-on and 19 PASS lines and looked exemplary. It surfaced only because the lead agent's independent session count disagreed with mine and we chased the difference instead of splitting it. **A cross-check against a differently-built instrument finds the class of error that self-audits are structurally blind to**, which is the whole argument for keeping one. Fixed by printing the resolved window and its day count on every run — the output now states the one fact that would have made the mistake visible.
- **Publish-then-relay makes a wrong number expensive fast.** Within about twenty minutes the figures had been divided into three weekly ratios, recorded in a CSV, and relayed onward to the user. Two of the three things I had to retract today were already downstream before I checked them. **When a number is going to be someone's denominator, spend the extra pass BEFORE handing it over** — and when you do retract, say which downstream artifacts are affected, not just that you were wrong.
- **When two independent scans disagree, compare RATIOS — the absolutes are usually different definitions (2026-08-28).** The lead agent and I decomposed the same two weeks of agent turns. Absolute lane counts differed 2-3x (we count a "turn" differently), which looks like a contradiction and isn't. The growth ratios are the comparable object: turns-per-lane replicated (2.07x vs 1.90x) and settled the question; parent-session counts moved in **opposite directions** (22→17 vs 24→29), which is a real disagreement and means one definition is wrong. **A direction disagreement is a finding; a magnitude disagreement is usually a units mismatch.** Reconcile definitions before either side acts on the term that diverged.
- **Check your own instrument before reporting a contradiction.** My first pass at that cross-check keyed the subagent lane off `parts[3]` of the event id — which is the per-file sequence number, not the lane — giving 1,362 "lanes" at 1.8 turns each and an apparent 11x discrepancy with the peer. Nothing errored. I caught it only because 1.8 turns per dispatched agent is implausible on its face. **When a cross-check disagrees by an order of magnitude, the prior should be that you parsed something wrong, not that they did** — and sanity-check the absolute value against what the thing being measured could physically be.
- **A measured blast radius beats an unmeasured fix.** That peer's hole was real but every affected row landed in a negative bucket — zero positives. Knowing the distribution makes it a baseline: if it ever shifts positive, something upstream changed.

## False-green tooling (2026-08-19)

- **A client-side success is not a capability.** After a respawn, `list_watched_docs` correctly returned `[]` (watches don't survive a restart — the server-side store never existed). Re-watching then returned success and an accumulating list, and `list_watched_docs` confirmed both docs. All fiction: `list_docs` and `get_doc` both failed with `live-feedback server not found`, and the discovery file `~/.claude/live-feedback/server.json` did not exist. `watch_doc` banks intent in the MCP child's memory and never contacts a server. **An empty list prompts action; a populated list ends the investigation** — so the healthy-looking failure is the more dangerous one. Verify a subscription with a call that must reach the server (`get_doc`), never with the subscribe call's own return value.
- **Re-watching is not a fix while the server is down.** The obvious remediation reports success and registers nothing, so it has to be redone once the server is back. Any "restore your watches" instruction issued during an outage produces a fleet of peers that all believe they're subscribed.

- **"Discovery file missing" means the server MOVED at least as often as it means the server died — and the two have opposite repairs.** The error text says `start it with \`bun run dev\``, which here would have raced a second server onto port 8787 against the healthy one; this fleet already has an entry about two servers binding one port in different address families and both succeeding silently. The server was up the whole time: a plugin rename moved discovery to `~/.claude/claude-workspaces/server.json` and deleted the old directory, so old-bundle clients reported "not found" against a running server. **Check for a listener on the port before believing the process is gone** (`curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<port>/`), and never follow a tool's own suggested remedy mid-cutover.
- **Before proposing a compatibility shim, read what the old client actually parses.** The 0.1.58 client reads only `j.port` and rebuilds `http://localhost:${port}`, so symlinking old→new discovery is schema-safe; and because `resolveBaseUrl()` runs per request inside `http()` rather than being cached at startup, the shim fixes every already-running child on its next call with no restarts. Its `catch {}` swallows a parse failure into the same "not found" error, so an incompatible file would have been indistinguishable from the outage it was meant to fix — which is exactly why the check is worth the two minutes.

## Bound-doc markdown round-trip (2026-08-19)

- **Live-feedback write-back mangles bare identifiers through the emphasis parser.** `wall_clock_hours` came back as `wall*clock*hours`; underscores are read as emphasis and re-serialized as asterisks. It is lossy in both directions — the same pass that degraded one identifier repaired a broken link, so a diff is not obviously "corruption" at a glance.
- **Backticks protect, bare prose does not.** In one file: 14 backticked `est_h` intact, 5 bare-prose ones corrupted to `est*h` in committed history. **Backtick every identifier in any doc that is or may become LF-bound** — this is the whole mitigation. Our methodology spec survived only because its identifiers happened to be backticked.

## Session identity across a respawn (2026-08-19)

## Shipped but unreachable (2026-08-19)

## A long measurement must outlive the session that starts it (2026-09-12)

- **A background job started by the agent dies when the agent's session restarts, and leaves no error.** The 22-week restatement sweep was killed mid-W26 by a session restart; `sweep.log` simply stopped, with the last line reading like a run still in progress. Nothing failed, nothing was logged, and the only way to tell a dead sweep from a slow one is `pgrep`. A 70-minute measurement is long enough that this is the *expected* outcome, not the unlucky one.
- **So detach anything that outlives a turn:** `nohup zsh script.sh >> log 2>&1 < /dev/null & disown`, then confirm with `ps -o ppid` that it reparented to **PPID 1**. The launch reporting success tells you nothing — same false-green shape as `watch_doc`.
- **Make the sweep idempotent instead of resumable-by-hand.** Each week's completion is testable from its own artifact (`grep -q "WEEK hands-on:" w<NN>.err`), so the resume script skips finished weeks and re-runs only the hole. That is what makes a restart cost the dead week and nothing else — and it is safer than re-running everything, because a completed week re-measured only resamples the ~2% run-to-run variance and makes the series *less* internally consistent.
- **A partial artifact must never look like a finished one.** W26's `.err` held a window line and an archive line and no figures. The collector now refuses to publish a series containing such a week and names it, because the failure that matters is not a crash — it is a 22-week trend quietly rendering 21 rows.
- **Under memory pressure the harness sheds its OWN background tasks, and that is a different killer from the OOM reaper (2026-09-15).** Four era runs died at the same point with "the system is running low on memory" — and so did a pure `sleep` loop, which cannot be an OOM victim. That one observation identifies the killer: it is the harness dropping tracked background work, not the kernel. Relaunched with `nohup … & disown` the same run sailed past the point all four died at. The controlled comparison arrived by accident an hour later: a harness-tracked waiter watching the sweep's log was killed with that exact message **while the PPID-1 sweep it was watching kept running**, same machine, same minute. So the detach in the entry above is not only about surviving a session restart — it is what makes a long job survive the harness's own memory shedding, and any waiter, monitor or poller you arm to watch that job is itself killable and will die first.
- **`Pages free` is the wrong gate on macOS and will never fire.** I armed a watcher for >120,000 free pages, calibrated on the single sample where a run had succeeded (213,086). It sat for 30 minutes and fired nothing: free pages were pinned at 3,500–4,000 the whole time while `memory_pressure` reported **36% system-wide free**, because macOS counts reclaimable inactive and compressed pages that `vm_stat`'s free line does not. A gate whose threshold the machine structurally cannot reach is indistinguishable from a healthy quiet watch — the same silence-is-not-success shape as a monitor that greps only for the happy path.
- **A completion marker has to be a line the run always prints.** The sweep's idempotence test grepped for `wrote epics:`, which is conditional, so a week that finished cleanly (exit 0, db written, audits run) was recorded as INCOMPLETE and would have been re-run on any restart — paying 40 minutes and ~$5 of fresh enrichment to redo finished work, and resampling the estimator in a way that makes the three weeks less comparable. Grep the source for the marker and check it is unconditional before trusting it; `wrote run db:` was the right one.

## Archive freshness is a gate, not a warning (2026-08-24)

- **The archiver died silently a second time** (Aug 17 20:49 → Aug 24, same launchd `exec` denial as Jul 15 — see Ops; it was misfiled as a TCC revocation at the time). The requested week had **zero** archived files while the live store had 676. The pipeline reads the archive by design, so the run would have reported an almost-empty week **with 100% coverage and no warning** — output that looks like a finding, which is what makes it the most dangerous thing this tool can emit.
- **So it is now `error: exit 2`, not a warning.** `archive_window_coverage()` counts files with mtime at/after the window start; transcripts are append-only, so a session live in the window must have an mtime in it. That makes zero files a *necessary*-condition failure — sound without parsing a single event. `--allow-stale-archive` is the escape hatch, off by default, because the entire failure mode is that nobody looks.
- **Two fixes, and only one of them is code.** The gate stops a wrong answer; it does not keep the archive alive. Keeping it alive means moving the interpreter and script off the second volume or off launchd — **not** granting Full Disk Access, which is what this file said until 2026-08-25 and which cannot work because the job dies at `exec`. See the Ops entry above.
- **The scheduled archiver has been dead since Aug 8 and the archive is current anyway, which is why nobody noticed.** `cli.py` shells out to `archive-transcripts.sh` before every run (the user's 2026-07-08 call: all analysis reads the archive, every request refreshes it first), and from a terminal it inherits the shell's disk access and succeeds. So archive freshness is a function of *someone choosing to run an analysis* — and the freshness gate, which only executes inside that same run, can only fire when the thing that repairs the problem has already run. **A gate that lives downstream of its own remedy cannot detect the remedy stopping.** The missing alarm is the one that runs when the pipeline does NOT: how much of the live store is unarchived, checked on a cadence well under the ~16-week live-store retention.
## Event-sampled liveness is milestone-clocked (2026-08-25)

Numbers, per-board tables and provenance: [2026-08-25-liveness-and-archive-audit.md](../research/2026-08-25-liveness-and-archive-audit.md).

- **Never trust `stat` in a scheduled check — read a byte.** Under launchd an Apple *platform* binary (`/bin/bash`, `/bin/ls`, `/usr/bin/rsync`) is denied on the second volume while a Developer-ID binary on that same volume reads fine: the gate is per-**binary**, not per-path. `stat` can succeed where `open` fails, so a stat-based probe passes on a volume it cannot read. **B11 opens a file for this reason — don't optimise it back.** Corollary: relocating a bash script off the volume is not the fix either; it dies on its first `rsync`.
- **B11/B11b: presence is not currency.** B11 counts live files never copied and alarms on the age of the oldest (21d, against ~16-week rotation). B11b catches what name-matching hides: transcripts are append-only, so a session that keeps growing stays "archived" by name forever. The sound assertion is that a transcript which **settled before the archiver last ran** must not be short in the mirror — anything newer is lag, not loss. Keying "settled" off `now` instead reports fabricated data loss on ordinary lag.
- **Key archive lookups by max-size-per-name, never `{name: path}`.** 256 session ids appear under more than one project dir (576 across the whole archive root). A 15KB copy shadowed the same session's fully-archived 130MB copy and produced a fabricated 136MB "permanent gap" that survived until it was re-derived a second way.
- **Any liveness check must run on a signal denser than the thing it detects.** Board activity is milestone-clocked — a burst when something lands, then nothing through the next build/debug loop. Transcripts are ~73x denser over the same window. A threshold set near the median inter-event gap of healthy work fires on most healthy work, by construction, and is not tunable out.
- **A gap histogram cannot indict a liveness proxy; only silence during provable activity can.** A long silence may be overnight or a human-gated hold. Restrict to spans where the subject was demonstrably working — that needs an independent witness — then measure the proxy's silence inside them.
- **Absence has three meanings and only one is information.** `grew since last check` = alive. `exists, unchanged` = nothing, until a baseline exists. `no file` = the watcher is blind, or the process never started — and fleet-wide that last case is the **modal** outcome of starting a process, so it can never be read as death.
- **Resolve a transcript by session id (`~/.claude/projects/*/<id>.jsonl`), never by constructing a path from cwd.** Worktree placement genuinely varies; a constructed path lands somewhere that never grows and reads as permanent death.
- **Generalize before publishing a number.** One board is one working mode. A single-operator board with multi-day approval holds inverts the result. When a metric is contested, lead with what survives the parameter sweep — and prefer the right variable (dependency state) over a better constant.
- **A measurement that kills a mechanism does not license its replacement.** The review measured that the window was wrong; it measured nothing about the three things proposed instead. Shipping unmeasured replacements is the same error pointed forward.

## The archive is the primary, not a mirror (2026-08-25)

- **53% of the corpus exists only in the archive.** 7,596 of 14,390 archived session ids are gone from `~/.claude/projects` entirely. Measured by diffing every live transcript id against every archived one, bucketed by week: there is a hard cliff at the week of **2026-05-04** — every week before it has **zero** live presence, every week after retains normally. The live store holds roughly **16 weeks**.
- **The week of 2026-04-13 is 4,283 files, the largest week in the whole corpus, and 100% archive-only.** That is the start of this project's documented clean-data range. So the archive is not a convenience mirror we read by preference — for most of the history this tool exists to analyse, it is the **only surviving copy**.
- **That makes a dead archiver two different bugs with two different clocks.** `archive_window_coverage()` (shipped 2026-08-24) catches the fast one: a window the archive cannot cover, so the run refuses rather than reporting a quiet week. It does **not** catch the slow one — live sessions aging out un-archived. The 8/17 outage lasted a week and the 8/17 week held 637 live sessions; had it lasted ~16 weeks those would have expired with no copy anywhere, and nothing in the pipeline would have said so. **Needs its own alarm: how much of the live store is not yet archived, checked on a cadence far shorter than retention.**
- **Retention was asserted as a cause before anyone measured it, and the first explanation was wrong.** 32 transcript-less session dirs on one repo were attributed to retention; they turned out to be sessions that ran their `SessionStart` hook and died before their first turn — the newest dated *yesterday*, while a four-week-old transcript sat untouched on disk. The hook fires and persists its oversized context for *any* `claude` start, including ones that never open a conversation. So **"no transcript anywhere" is the MODAL outcome of starting a process**, not a signal — which makes the liveness rule stronger, not weaker: a watcher that reads a missing file as death fires on the overwhelming majority.
- **An artifact proves a process ran, never what it did or why it stopped.** Second miss of this shape in one day: the morning's was counting placements as subjects (10 dirs, 1 session); this one counted a directory's existence as a session's fate. ## Never invent an id a store already has (2026-09-12)

- **Third time this exact defect has shipped.** `(session, seq)` collided across subagent lanes and destroyed 80% of a fan-out session; live-feedback events were keyed `live_feedback:live-feedback:<docId>:0` — the DOCUMENT as identity, `seq` always zero — so dedup kept one event per doc: **5,699 read sessions → 1,180, 2,560 comments → 475**, one doc visited 58 times becoming one event. **Before constructing an event id, dump one raw record and look for the store's own.** The activity stream had `eventId` on 5,699 of 5,699 records the whole time.
- **Pass it through with a source prefix rather than trusting it globally.** `metadata["source_event_id"]` wins over the derived id, and `event_id` renders it as `<source_system>:<id>` so two stores cannot collide on a same-shaped id. Derived ids for sources that have none stay byte-for-byte identical, which is what lets a fix like this ship without shifting anything already persisted (review verdicts and task-id carry-forward are keyed on them).
- **A record id that is unique "within a thread" is not a key.** 25 of 2,535 distinct comment ids repeat across the store. The key is `comment:<docId>:<threadId>:<commentId>`. Check uniqueness on the real store before keying on a field, not on the three records you looked at.
- **The negative test is the one that proves the fix, so write both.** Of 7 tests, 5 fail without the change and 2 pass with and without — a genuine duplicate still dedupes, and transcript ids are unchanged. A dedup fix that quietly disables dedup passes every "N visits yield N events" test ever written.
- **Recovering discarded events un-masks whatever the discarding was hiding.** Dedup had been throwing away 4 of 5 read sessions, including other people's: over all history **1,031 sessions / 22.6h** of `isOwner: false` `Anon-*` reading sat in the user's hands-on, and the collapse was accidentally deleting most of it. A fix that makes a pipeline more complete makes every downstream filter gap more expensive at the same moment. **Re-audit the filters on a source the moment you increase its volume.**
- **And the allowlist had never matched his main handle.** `HUMAN_NAME_FRAGMENT` set to his first name does not match his primary handle — 1,054 of 2,938 of his own comments (29%) have never counted, in the filter written to stop *machines* being counted as him. A one-fragment allowlist is one identity; people have several. Prefer the structural field where the store has one: `actorName` and `isOwner` agree on 5,687 of 5,699 read sessions (99.8%), and `isOwner` needs no name list at all.
- **Scope discipline: a dedup fix may not redefine the data subject.** Who counts as the user is a definition change and his call — measure it, file it, say what it is worth, and do not fold it into the PR that found it.

## The field a ruling names is not always the field that decides (2026-09-12)

- **A ruling was implemented, correct, and a measured no-op, because the field it named barely exists.** "Board before the file-path `sourceUrl`" — but `sourceUrl` is on **161 of 7,587 docs (2.1%)**, and **none of those 161 also carries a board**, so that branch never competes. The signal that actually contests the board is the working directory from `.index.json` (532 docs carry both). Reordering the named branch alone moved zero docs. **Before implementing a precedence rule, count how often the two signals are both present** — a rule between two things that never co-occur is a rule about nothing.
- **The spec's own blast radius was measured against that same wrong field and read plausible.** "470 docs carry both a file-path source and a board … 133 genuinely disagree … about 8 route worse." The shape was right (7 docs route worse, and the two it named by category are 2 of the 7); the mechanism was wrong. A number that survives review because it sounds like the right order of magnitude has not been checked.

## An orphan contributes nothing, so recovering one moves a published number (2026-09-12)

- **Attaching events is not bookkeeping — an event attached to no task is an event whose hours nobody counts.** The workspace `taskId` join attached 1,424 previously-orphaned events, and the week's hands-on went **24.3h → 28.5h (+17%)**. The rise is 236 `review_session` events at ~64s mean: 236 x 64s ≈ 4.2h against a measured +4.18h, which is what makes it recovered measurement rather than a new model.

Two numbers moving in the ratio you predicted beats either one moving in the direction you hoped.
- **Join on the identity, then stop.** 48 of 222 workspace tasks are split across more than one weekly-review task, one of them eight ways. Merging those is a re-segmentation that moves published hours for a reason nobody measured — so the pass **never moves an already-attached event**, reports the split count, and leaves it. The negative test earns its place: 5 of 8 tests fail if the already-attached guard is removed.

- **Stamp the resolution, never leave the field absent.** Every doc event now carries `task_resolution` (`task-card` or `no-task`). An absent field cannot be told apart from an extractor that forgot to look, which is how a coverage number counts a bug as a clean miss.
- **Print the coverage number every run, not only when it trips.** The unrouted bucket used to print only past 5%, so a reader had no way to tell "healthy" from "the check stopped running" — the exact shape of the 26%-behind-100%-coverage failure. Silence is not a value.

## Two instruments, two tolerances — and the union that keeps them honest (2026-09-12)

- **A tolerance that points inward is a better assumption, not the absence of one.** The block rule (same key, gap ≤ G, span = first event to last, nothing added at either end) can only join two things he actually did; it can never invent time outside them. That is why it beats a symmetric modelled window on a stream that records interaction directly. It is still a tolerance: G bridges every sub-G silence as work. **Never describe it as "no tolerance"** — G=0 is 22.61h and G=300s is 30.34h on the same week, which is the whole argument for printing the knob on every run.
- **Run-length blocking over the GLOBALLY sorted stream, not per-key grouping.** Any key switch cuts the block. Per-key grouping bridges a gap during which he is on record doing something else, which is exactly the padding the rule exists to remove. Five attempts to reproduce a published 25.06h by guessing the method got as close as 23.75h; finding the ORIGINAL script in the session transcript reproduced the whole G-sweep to the digit in one pass. **When a number was produced by a script, recover the script — do not re-derive the method from its output.**
- **Two substantive bugs only surfaced because the reproduction failed.** 1,662 person activity touches (`doc_open`, `comment`, `reply`, `resolve`, `reopen`) had never been ingested — they carry no duration, so they cost nothing under a modelled-window metric and everything under a block rule, because bridging is all they do. And `durationMs` ≠ `endTs − startTs` on read sessions: 21.07h vs 23.01h over the same 1,293 sessions, 1,240 of them differing by more than a second. The window model wants the former, the block rule the latter, so the extractor now carries both.
- **Block the whole week once, then let tasks claim blocks.** Blocking inside one task's own events cannot see the events that interrupt it, so a task bridges a gap the week knows he spent elsewhere and reports a figure that cannot be reconciled with the week's. One global partition plus an index from event → block is also the difference between linear and quadratic.
- **A per-task sum SMALLER than the week-wide union is a coverage hole, not a broken union.** 29.06h week-wide against 16.6h summed per task, because only 10.78h of the 25.06h workspace union lands on any weekly-review task — 1,984 workspace events have no sibling evidence in the window to attach to. Sum ≥ union only holds when the parts cover the whole; print the attached share so nobody reads the inversion as arithmetic failing.
- **Compare like with like when naming what a number replaces.** The new week-wide union is 29.06h and the old per-task presence SUM is 28.5h — near-identical, and the agreement is meaningless. Measured the same way, presence week-wide is 46.95h, so the honest statement is that the block rule removes 17.89h (38%) of modelled padding. A comparison between a union and a sum flatters whichever side was summed.
- **Print the union and the sum together, every run.** "Unioned, never added" is unfalsifiable from a single total. Two numbers and a difference make it checkable by a reader who was not here — same argument as printing the unrouted bucket even when it is healthy.

Against what actually shipped, the ruling moves **-3.55h (-2.8%)** over all history and **0.00h inside the era** — the era weeks were already counted, so the ruling's real work is dropping other people's reading in the weeks either side. ## Measuring the time a keyboard cannot see (2026-09-12)

- **A ticket's premises are measurements of a moment, and two of this one's had already rotted.** It named `meeting.json` as the coverage denominator (24 of 42 dirs) — but it is a rollup and no duration is read from it; the ledger is `meetings.jsonl` and **42 of 42** dirs have one. That is the point: the day a recorder is killed mid-meeting, a zero-length event reports an unmeasured meeting as a meeting that did not happen — the quietest lie this tool can tell.
- **A recording is worth its ledger span, not its speech.** Over the 54 turn files with timestamps the spoken span is 4.22h against the ledger's 5.24h: **19% is recorded and not spoken.** Pauses, reading, somebody else talking off-mic. Carrying every turn's own timestamp (not a first/last summary) is what lets a reader tell an hour of talking from a recorder left running — the summary cannot distinguish them and the list can.

Filtering on either field would delete real meetings to enforce a field the store fills in half the time. It is his recorder on his machine; the measurement is his presence, not who spoke.
- **Word counts are the most a time model can learn from a sentence without becoming a place that stores it.** Meeting turns carry third parties' names and their personal and medical business, and the ledger's `speakers` records carry real names outright — a doctor's among them. Length is what makes a turn evidence somebody was talking; the words add nothing an hours figure can use. The one spoken field this repo does keep is a `voice.request` transcript, because it is *his*, dictated to his own board, which is the same act as typing to it.
- **"+0.00h" is the shape a silent drop makes, so prove a null before publishing it.** 88 voice requests moved the union by exactly zero — because all 88 were keyless, and `workspace_blocks` skips a keyless event **entirely**: it contributes nothing AND bridges nothing, and the result is indistinguishable from never having ingested it. An empty attribution key is not "blocks alone"; it is invisible. With a board fallback the real figure is +0.06h. Second time this month that going to *prove* a no-movement claim is what found the movement.
- **And 7 of the 88 named their task in `context.taskId`.** Not one carries the top-level `taskId` every other board record has. Reading only the level you already knew about drops them silently — the same defect as `(session, seq)` across subagent lanes and the doc-keyed live-feedback ids, for the **third** time in this repo. Dump one raw record of a new family even when you already parse its file.

Expect a signed delta from an addition; an unsigned "it can only go up" intuition is wrong here by construction.

A source that closes a measurement gap going forward does nothing for the history, so the restatement has to say which weeks had the instrument and which only had a keyboard.

## Mutation testing, and the stale `.pyc` it manufactures (2026-09-12)

- **A test that passes the moment you write it has proved nothing.** The billing suite passed 10/10 on first write; 15 single-line mutations then showed every one of them notices something (client filter dropped, task title rendered into the artifact, `billing_status` always billable, era exemption removed, the CLI command reached but doing nothing). That last one is the check worth keeping — a function correct, tested and never called is a defect this repo has shipped before, and only a call-site test sees it.
- **Restoring the source is not enough: clear `__pycache__` between mutations.** CPython validates a `.pyc` against the source's **(mtime, size)** at 1-second granularity, and the natural mutations are the same size as what they replace (`return 2` → `return 0`). A rewrite inside the same second therefore leaves a `.pyc` that runs the OLD bytecode while `inspect.getsource` prints the NEW file — so the harness reported a fabricated failure, `sys.settrace` showed `return 2` executing and returning `0`, and every source-reading check agreed the code was fine. **When the source and the behaviour disagree and both look right, suspect the bytecode cache before the logic.**
- **Do not mutate a dispatch by deleting it when the fallthrough is expensive.** Removing `if args.billing_export: return _cmd_billing_export(...)` sent `main()` into `_cmd_digest`, i.e. a full pipeline run — archive refresh, extraction, LLM enrichment — from inside pytest. Short-circuiting it to `return 0` proves the same thing and launches nothing.
- **A guard written as a bare substring fires on ordinary prose and gets deleted rather than fixed.** The "no revenue figure" check banned the word `rate`; the methodology footer says "sums each agent sepa*rate*ly". Ban money-shaped tokens (`$`, `hourly rate`, `amount due`), and where the artifact must be able to NAME what it omits, assert a count and the line it appears on rather than absence.

## Attachment is not authorship (2026-09-15)

- **A task holding an artifact is not a task that produced it, and two separate checks were built on the assumption that it is.** The LoC audit priced a task against an 11,489-line rollup PR it held only the `pr_merged` event of — no opening, no commit — against 0.66h of wall clock. The 15-minute-gap research read "a commit is timestamped inside the silence" as proof the agent was working; the commit was a 33-line unattended daily digest, the session emitted nothing for 62 minutes, and it resumed 9 seconds after the user sent it a new message. Same premise, two instruments, found on the same afternoon.
- **Ask which event of an artifact's life the task holds.** Opening a PR or committing to it is participation; watching it land is not. And a merged PR supersedes an abandoned one of the same change — a task holding #13 (opened, abandoned, 1,718 lines) and #14 (opened and merged, 828) is holding one change under two numbers. Those two rules took the LoC flags on the three era weeks from 1/2/6 to 0/0/1 without moving a single threshold.
- **The witness for "was it working" is the transcript, and it has to be lane-aware.** Of 10 artifact-witnessed gaps, 0 had the task's own lane active; 8 had events only in sibling lanes of the same session, every one attached to a *different* task — so bridging would bill this task for time another task already carries. The artifact test found 10 cases and was right about none of them.
- **Counting the human's own message as agent activity made every case read as work.** The first version of the re-test asked "was anything in this session inside the silence" and got 1 event for the 62-minute case — the user's message, which is what ENDED the silence. A witness for "the agent was working" must filter to `actor == "agent"`, and a witness for "this lane" is vacuous, because the lane being silent is what makes the gap.
- **A correction that makes the tool look better is still a correction.** Undercount went from 0.8h/3.1h/3.5h to 0h/0.3h/1.4h — the 15-minute rule is more defensible than the doc claimed, and the two errors no longer cancel. A finding in your own favour deserves the same re-test as one against you; this one only surfaced because the user asked what the agent was doing for an hour.

## A sum of spans is not elapsed time (2026-09-15)

- **Check an hours figure against the length of its own window before anything else.** The worksheet sums per-task `wall_clock_hours` into each epic row and into the window block, then divides expert hours by it to publish wall-clock speedup. Tasks genuinely overlap, so a clock minute is counted once per live task — and two of the three era weeks therefore report **246.18h and 329.47h of wall clock inside 168-hour weeks**. The spec defines the metric as "time during which SOMETHING was happening", so exceeding the window falsifies it with no model and no threshold. Sum ÷ union is 1.58x / 2.44x / 2.70x.
- **This is the same bound `learnings.md` already demanded for hands-on, and the answer is an order of magnitude different.** Presence sums ~4% over its union, which is why a weekly hands-on total is defensible. Wall clock sums 60–170% over, because concurrency is the very thing the metric is measuring. **A bound measured for one metric says nothing about another metric on the same tasks.**
- **It concentrates in fan-out, so a spot check on a quiet project clears it.** 13 of 14 April projects are within 5% of exact; `claude-live-feedback-plugin` is 2.13x (Aug, 227 tasks) and 1.97x (Sep, 257). Sample the busiest group, never a representative one.
- **The repo already had the vocabulary and used the wrong word.** `agent_hours` (merged timeline, elapsed) vs `agent_labor_hours` (per-lane, summed) is exactly this distinction, published with the ratio as a parallelism factor. The summed wall clock is not meaningless — it is wall-clock *labor*. The defect is publishing it under the elapsed metric's name and dividing expert hours by it.
- **Per-task was right the whole time, which is why nothing caught it.** Every per-task wall clock is a correct union, every unit test passes, and the post's headline (a median over single tasks) is unaffected. The error lives only in aggregation, so it is invisible to any check that reads one task.
- **A correction can be upward, and that deserves the same scrutiny as a downward one.** Unioning would move whole-week speedup 3.63x → 5.72x, 3.77x → 9.21x, 2.62x → 7.07x. The user has ruled he would rather the multiplier read low than high, so a fix that roughly doubles a lead metric is his call even though the current denominator is arithmetically impossible.

## Measure the instrument's noise before designing the A/B (2026-09-15)

- **A change whose effect is smaller than the instrument's own spread cannot be validated by re-running the instrument, and the re-run will still produce a number that looks like a result.** PR #84 changed the estimator prompt; the April week re-ran at Σest 194.1h against 203.0h, a tidy-looking −4.4%. The estimator's own run-to-run standard deviation, already measured at 11.3% over 27 runs of another week, is more than twice that. The comparison was as clean as one gets — same window, same 103 tasks, hands-on identical to the hundredth of an hour, only the prompt different — and it still could not answer the question it was run to answer. **Check the effect size against the noise floor before paying for the run, not after.**
- **A cache hit is not a second sample.** Five pre-change runs of that week agreed to within 0.8% (Σest 203.0–204.7h, 0–3 of 103 tasks differing), which reads as excellent reproducibility and is nothing of the kind: the enrichment cache keys on the system prompt, so an unchanged prompt serves the same answers back. The tight agreement was one sample printed five times. **Before quoting a spread across runs, check whether the runs could have differed** — and note the corollary, that the only runs that CAN disagree are the ones where something changed, so a cache makes the noise structurally invisible exactly when you want to measure it.
- **Test the mechanism the commit named, not the one you remember.** I tested the re-run against "attachment is not authorship" — a real finding, from earlier the same evening, about tasks holding artifacts they never opened. PR #84 is a different change entirely (price every shipped front, not the last; exclude rework). The wrong test returned a crisp, publishable-looking answer: exactly one task in the week fits the mechanism, so the change did one thing worth −4h. Re-reading the commit diff invalidated the whole analysis. **A stat that comes out clean on the first try is a reason to re-read the premise.**
- **The instruction landed and the number went the other way, which is the finding.** Shipped fronts named per task nearly doubled (≈2.0 → ≈3.5, on 68 of 103 tasks), so the prompt edit demonstrably took effect — and the 68 tasks naming more fronts fell 6.00h between them, against a commit message predicting a rise. The 10 tasks whose prose describes rework rose 1.75h, against a prediction of a fall. **Verify that a prompt instruction was obeyed separately from verifying that it had the intended effect**; they are two claims and here they came apart.
- **Five cases that agree with a story are not evidence for it.** Reading the five biggest drops, every new rationale itemised — named each front, priced it small, summed — where the old one described the work in aggregate and landed on a round number. A compelling mechanism, and false: across all 103 tasks the estimates fell whether the rationale gained hour figures (−4.35h over 25 tasks), kept the same count (−2.78h over 63), or lost some (−1.75h over 15), and per task the three groups are indistinguishable. What the drop actually tracks is the size of the estimate being re-rolled (under 1h +0.05h, 1–3h −0.05h, 3–6h −0.28h, above 6h −0.90h) — a broad proportional nudge, which is equally what a more conservative estimator and a noisy re-roll look like. **Sampling the extremes is how you find a hypothesis, never how you confirm one.**

## A subgroup statistic quoted without its subgroup is a fabricated figure (2026-09-16)

## The run db is written from the trace, not from event_ids (2026-09-18)
